## 1. 구현

- 기획서/테이블정의서에 있는 API·컬럼만 가정한다
- `userId` 등 신원은 쿼리/바디가 아니라 **JWT(`@AuthenticationPrincipal`)** 에서만 가져온다
- 동시성·비정규화 카운트는 문서(`database-design.md`) 기준으로 UPDATE 쿼리 등을 쓴다
- 프론트 액션이 이미 있으면 계약(경로·메서드·204/에러)에 맞춘다
- **새 라이브러리·의존성** (npm/Gradle 등)은 추가하기 전에 사용자에게 물어보고, 동의한 뒤에만 쓴다. 이미 프로젝트에 있는 것만 기본으로 사용한다
- 구현이 끝나면 **리뷰할 파일 목록**을 호출 순서(또는 의존 순서)로만 짧게 나열한다. 설명은 아직 하지 않는다

## 2. 코드 리뷰·해석 — 파일 1개 = 리뷰 1회

한 번에 여러 파일을 설명하지 않는다. **파일 하나씩**.  
비유만 길게 쓰지 말고, **코드를 보여 주며** 메서드·매개변수·호출 흐름을 푼다. 생활 비유는 **코드 설명 옆에 짧게** 붙이는 양념이다.

### 규칙

- **1회 응답 = 파일 1개** (다른 파일 본문 인용 금지. “앞에서 넘어옴 / 다음에 넘김”만)
- **import / package 선언은 제외**
- **코드 인용 필수** (`startLine:endLine:path`). 말로만 설명하지 않음
- **인용 코드에 주석** — 리뷰용으로 보이는 코드 블록에 줄 역할 주석을 달아 줌 (원본 파일에 없는 설명 주석도 리뷰 블록 안에만 추가 가능)
- **메서드 단위**로 리뷰 (이 메서드가 뭐 하는지 → 매개변수 → 안쪽 흐름 → 어디로 넘기는지)
- **생활 비유**는 코드 설명 **옆 한 줄** (카페·택배·출입카드 등). 비유만 길게 쓰지 않음
- **말투** — `~다` / `~한다` / `~않는다` 로 끝내지 않음. `~음` / `~함` / `~됨` / `~임` 체로 씀. **문장 끝 마침표(`.`) 쓰지 않음**
- 전문 용어는 그 줄 코드 옆에서 비유로 한 번만 풀음
- 끝에는 `다음 파일: …` 또는 `이 단계 파일 리뷰 끝`만 적고 **멈춤**
- 사용자가 「다음」하기 전에는 다른 파일·다음 기능으로 넘어가지 않음

### 한 파일 리뷰 구성 (이 순서)

1. **파일 한 줄** — 이 파일이 전체에서 맡는 역할 + 짧은 비유 한 줄
2. **호출 흐름 한 줄** — `이전 → 이 파일(메서드) → 다음` (코드 이름 사용)
3. **이번 기능에서 볼 메서드 목록** — 이름만 나열
4. **메서드마다 반복**:
   - 코드 블록 인용 (+ 주석 단 버전)
   - 이 메서드가 하는 일
   - **매개변수는 아래「매개변수 5문답」으로 하나씩** (이름이 같아도 파일이 바뀌면 다시)
   - 메서드 안 줄 흐름 (호출·return·분기)
5. **이 파일 한 줄 요약**

### 매개변수 5문답 (사용자가 제일 헷갈리는 부분 — 매번 이 순서로)

매개변수 = **함수/메서드 안으로 들여보내는 재료**  
*(요리할 때 주방에 넘기는 재료 목록 · 재료마다 “어디서 왔고 뭐에 쓰나”가 다름)*

**중요:** 같은 이름(`userId`, `feedId`)이라도 **지금 이 메서드 입장**에서 다시 묻기  
컨트롤러의 `feedId`와 서비스의 `feedId`는 값이 같아도 “누가 채워 줬는지” 설명이 한 칸 더 깊어짐

각 매개변수마다 짧게 답함:

| # | 질문 | 답할 때 쓸 말 |
|---|------|----------------|
| 1 | **이름·타입이 뭐임?** | 예: `Long feedId` |
| 2 | **누가 채움?** | ① 사용자 요청(URL/쿼리/바디) ② 로그인 티켓(JWT/쿠키) ③ 바로 위 메서드가 넘김 ④ DB에서 읽음 ⑤ 코드 상수 중 하나라고 **명시** |
| 3 | **사용자가 마음대로 조작 가능?** | URL 숫자는 가능 · JWT userId는 조작하면 안 되고 서버가 쿠키에서만 읽음 이라고 구분 |
| 4 | **이 메서드 안에서 어디에 쓰임?** | 예: `insertIgnore(userId, feedId)` 첫/둘째 인자 · if 조건 · return |
| 5 | **다음으로 누구한테 넘어감?** | 예: Repository / 안 넘어가고 여기서 끝 |

한 줄 요약 공식 (복붙용):

`[이름] ← [출처 ②] · 사용자조작 [가능/불가] · 여기서는 [쓰임] · 다음은 [다음 행선지]`

예시:

- `feedId` ← URL path · 사용자조작 가능 · 여기서는 어느 글인지 · 다음은 insertIgnore 둘째 인자  
- `userId` ← JWT(쿠키)→컨트롤러가 넘김 · 사용자조작 불가(쿼리 userId 무시) · 여기서는 누가 찜했는지 · 다음은 insertIgnore 첫째 인자  

사용자가 “이 매개변수 요청에서 오는 거임?”이라고 물으면 **2번·3번만** 다시 풀어서 답함

### 권장 순서 예 (백엔드 API)

1. Controller → 2. Service → 3. Repository (필요 시 Entity)  
4. 프론트는 액션 → 훅/컴포넌트 순

필터·공통 유틸은 **그 단계에서 새로 손댄 파일만** 리뷰 목록에 넣는다.

## 3. 보안 · 예외 · 경우의 수

**파일 리뷰를 모두 마친 뒤** 한 번에 짧게 정리한다. (파일마다 반복하지 않음)

| 항목 | 확인할 것 |
|------|-----------|
| 인증 | 비로그인 401, principal null 방어 |
| 인가 / IDOR | URL·쿼리로 남 계정 사칭 불가 |
| 멱등 | 같은 요청 재호출 시 count 이중 증가 등 없는지 |
| 없는 자원 | 404 / 삭제·HIDDEN 처리 |
| 동시성 | UNIQUE / ON CONFLICT / 원자적 UPDATE |
| 에러 형식 | 프론트가 처리할 수 있는 코드·메시지 |
