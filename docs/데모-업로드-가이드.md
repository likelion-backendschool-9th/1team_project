# 데모 업로드 — 동작 원리 & 업로드 가이드

## 한 줄 요약

찍먹의 데모는 4가지 유형을 지원한다: **프론트엔드 데모** (zip 업로드), **백엔드 실시간 데모** (API 탐색기), **백엔드 리플레이 데모** (시나리오 재생), **외부 링크** (URL 등록).

---

## 1. 데모 유형 한눈에 보기

| 유형 | 업로더가 하는 것 | 찍먹이 하는 것 | 서버 필요 |
|------|---------------|--------------|----------|
| **프론트엔드 데모** | `npm run build` → zip 업로드 | 정적 파일 서빙 | X |
| **백엔드 실시간** | 서버 배포 → URL + openapi.json 등록 | API 탐색기 자동 생성 | O (업로더 서버) |
| **백엔드 리플레이** | 시나리오 JSON 등록 | 단계별 요청/응답 재생 | X |
| **외부 링크** | 배포된 URL 등록 | iframe 또는 새 창 | O (업로더 서버) |

---

## 2. 프론트엔드 데모 (zip 업로드)

### 2-1. 전체 흐름

```
업로더                          찍먹 서버                    체험자
  │                               │                          │
  │  1. zip 업로드                │                          │
  │──────────────────────────────>│                          │
  │                               │  2. 압축 해제            │
  │                               │  3. 파일 검사            │
  │                               │     (확장자, 용량, 악성코드)│
  │                               │  4. /demos/{id}/ 에 저장  │
  │                               │                          │
  │                               │  "찍먹하기" 클릭          │
  │                               │<─────────────────────────│
  │                               │                          │
  │                               │  5. 정적 파일 서빙        │
  │                               │  (Nginx가 index.html 응답)│
  │                               │─────────────────────────>│
  │                               │                          │
  │                               │         브라우저에서 실행  │
```

### 2-2. 서버가 하는 일

1. zip 파일 수신
2. 압축 해제
3. 허용된 확장자만 있는지 검사
4. 용량 제한 검사
5. VirusTotal API로 악성 코드 검사
6. `/demos/{demoId}/` 경로에 파일 저장
7. Nginx가 해당 경로를 정적 파일로 서빙
8. 체험자가 "찍먹하기" 누르면 `https://demo.dipsource.com/{demoId}/index.html` 열림

→ 특별한 실행 엔진이 필요한 게 아니라 **파일을 HTTP로 서빙하는 것**이 전부.

### 2-3. 업로더가 하는 일

#### 프론트엔드 프로젝트인 경우

```
npm run build  (또는 yarn build)
    ↓
build/ 또는 dist/ 폴더가 생성됨 (이미 HTML/CSS/JS로 변환된 상태)
    ↓
이 폴더를 zip으로 압축
    ↓
찍먹에 업로드
```

어떤 프레임워크를 쓰든 빌드하면 전부 HTML/CSS/JS가 됨:

| 개발할 때 | 빌드 명령 | 빌드 후 결과물 (이걸 업로드) |
|----------|----------|--------------------------|
| React + TypeScript | `npm run build` | build/ → index.html + bundle.js + style.css |
| Vue + SCSS | `npm run build` | dist/ → index.html + bundle.js + style.css |
| Svelte | `npm run build` | build/ → index.html + bundle.js + style.css |
| Angular | `ng build` | dist/ → index.html + bundle.js + style.css |
| 바닐라 JS | 빌드 필요 없음 | 그대로 zip으로 압축하면 됨 |

#### 풀스택 프로젝트에서 프론트만 뽑는 경우

백엔드에 의존하는 부분을 **Mock 데이터로 대체**한 데모 버전을 만들어야 됨.

**예시 1 — API 호출을 Mock으로 대체:**

```javascript
// 원본: 서버에서 메시지 가져옴
const res = await fetch('/api/messages');
const messages = await res.json();

// 데모 버전: 샘플 데이터 하드코딩
const messages = [
  { user: "김개발", text: "안녕하세요!", time: "14:30" },
  { user: "이코딩", text: "채팅 테스트입니다", time: "14:31" },
];
```

**예시 2 — 로그인을 Mock으로 대체:**

```javascript
// 원본: 서버에 로그인 요청
const res = await fetch('/api/auth/login', {
  method: 'POST',
  body: JSON.stringify({ email, password })
});

// 데모 버전: 아이디/비번 상관없이 성공 처리
function login(email, password) {
  return {
    success: true,
    token: "demo-token-12345",
    user: { name: "테스트 유저", email }
  };
}
```

**예시 3 — WebSocket을 setTimeout으로 대체:**

```javascript
// 원본: WebSocket으로 실시간 메시지 수신
const ws = new WebSocket('ws://localhost:8080/ws');
ws.onmessage = (e) => addMessage(JSON.parse(e.data));

// 데모 버전: 타이머로 메시지 시뮬레이션
const demoMessages = [
  { user: "김개발", text: "안녕하세요!", delay: 1000 },
  { user: "이코딩", text: "반갑습니다!", delay: 2500 },
  { user: "김개발", text: "데모 테스트 중입니다", delay: 4000 },
];

demoMessages.forEach(msg => {
  setTimeout(() => addMessage(msg), msg.delay);
});
```

### 2-4. 실행 가능 / 불가능

| | 실행 가능 | 실행 불가능 |
|---|---------|-----------|
| 언어 | HTML, CSS, JavaScript | Java, Python, Go 등 서버 언어 |
| 프레임워크 | React, Vue, Svelte 등 (빌드 후) | Spring Boot, Django, Express (서버 프로세스 필요) |
| 데이터 | JSON 파일, localStorage, 하드코딩 | PostgreSQL, MySQL 등 DB 직접 접근 |

핵심: **브라우저가 이해하는 것만 실행 가능.** 서버 사이드 코드는 직접 실행 불가능.

### 2-5. 제한 사항

| 항목 | 제한 |
|------|------|
| 허용 확장자 | html, css, js, json, png, jpg, jpeg, svg, gif, ico, woff, woff2 |
| 최대 용량 | 50MB (논의 필요) |
| 진입점 | index.html이 zip 루트에 있어야 함 |
| 외부 API | CORS 정책에 따라 안 될 수 있음 |
| 악성 코드 | VirusTotal API로 업로드 시 자동 검사 |

## 3. 백엔드 실시간 데모 (API 탐색기)

### 3-1. 개념

백엔드 개발자는 이미 springdoc 같은 도구로 Swagger 문서(openapi.json)를 만들고 있음. 이걸 그대로 활용해서 **API 탐색기 UI를 자동 생성**하는 방식.

방문자가 `GET /api/posts` 같은 걸 클릭하면 실제 응답 JSON이 바로 보임. 화면 대신 **요청을 보내고 응답을 받아보는 것**이 백엔드의 "찍먹"이 됨.

### 3-2. 전체 흐름

```
업로더 (백엔드 개발자)                   찍먹 서버                  체험자
  │                                       │                         │
  │  1. 본인 서버 배포                     │                         │
  │     (Render, Railway, AWS 등)          │                         │
  │                                       │                         │
  │  2. 찍먹에 등록:                       │                         │
  │     - 서버 URL                        │                         │
  │     - openapi.json 경로              │                         │
  │──────────────────────────────────────>│                         │
  │                                       │                         │
  │                                       │  3. openapi.json 파싱   │
  │                                       │  4. API 탐색기 UI 생성  │
  │                                       │     (엔드포인트 목록,    │
  │                                       │      파라미터, 응답 형식)│
  │                                       │                         │
  │                                       │  "찍먹하기" 클릭         │
  │                                       │<────────────────────────│
  │                                       │                         │
  │        체험자가 GET /api/posts 클릭    │                         │
  │<──────────────────────────────────────│ (프록시로 요청 전달)     │
  │  응답: 200 OK [...] ────────────────>│                         │
  │                                       │  5. 응답 JSON 포맷팅    │
  │                                       │─────────────────────────>│
  │                                       │        예쁘게 표시       │
```

### 3-3. 업로더가 하는 일

**1단계: 서버 배포**

본인의 백엔드 프로젝트를 아무 호스팅 서비스에 배포한다.

| 서비스 | 무료 플랜 | 특징 |
|--------|---------|------|
| Render | O | Spring Boot 지원. 무료 플랜은 15분 미사용 시 잠듦 |
| Railway | O (크레딧) | Docker 지원. 월 $5 크레딧 |
| Fly.io | O | Docker 기반. 256MB 무료 |
| AWS EC2 | 프리 티어 | 가장 자유로움. 설정이 복잡 |

**2단계: springdoc 설정 (Spring Boot 기준)**

```xml
<!-- build.gradle 또는 pom.xml -->
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>2.8.0</version>
</dependency>
```

이 의존성 하나면 자동으로 생성됨:
- Swagger UI: `https://내서버/swagger-ui.html`
- OpenAPI JSON: `https://내서버/v3/api-docs`

**3단계: 찍먹에 등록**

| 입력 항목 | 예시 |
|----------|------|
| 서버 URL | `https://my-chat-api.onrender.com` |
| OpenAPI 경로 | `/v3/api-docs` (기본값) |
| 데모 제목 | "실시간 채팅 API" |
| 설명 | "JWT 인증 + WebSocket 채팅 서버" |

### 3-4. 찍먹이 자동으로 만들어주는 것

openapi.json을 파싱하면 아래 정보가 전부 들어있음:

```
API 탐색기 화면 (자동 생성)
┌─────────────────────────────────────────────────────────────┐
│  실시간 채팅 API — @김개발                                    │
│  서버: https://my-chat-api.onrender.com    🟢 온라인          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  📁 Auth                                                    │
│  ├─ POST  /api/auth/login        로그인            [실행]   │
│  └─ POST  /api/auth/refresh      토큰 갱신          [실행]   │
│                                                             │
│  📁 Posts                                                    │
│  ├─ GET   /api/posts             글 목록 조회        [실행]   │
│  ├─ POST  /api/posts             글 작성            [실행]   │
│  ├─ GET   /api/posts/{id}        글 상세 조회        [실행]   │
│  └─ DELETE /api/posts/{id}       글 삭제            [실행]   │
│                                                             │
│  📁 Comments                                                 │
│  ├─ GET   /api/posts/{id}/comments  댓글 목록        [실행]   │
│  └─ POST  /api/posts/{id}/comments  댓글 작성        [실행]   │

├─────────────────────────────────────────────────────────────┤

│  ┌─ Request Body ────────────────────────────────────────┐  │
│  │  {                                                    │  │
│  │    "email": "test@test.com",                          │  │
│  │    "password": "1234"                                 │  │
│  │  }                                                    │  │
│  └───────────────────────────────────────────────────────┘  │
│                                              [요청 보내기]   │
│                                                             │
│  ┌─ Response (200 OK) ───────────────────────────────────┐  │
│  │  {                                                    │  │
│  │    "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6...",       │  │
│  │    "user": {                                          │  │
│  │      "id": 1,                                         │  │
│  │      "email": "test@test.com",                        │  │
│  │      "nickname": "김개발"                              │  │
│  │    }                                                   │  │
│  │  }                                                    │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

| 자동 생성 항목 | openapi.json에서 가져오는 정보 |
|--------------|----------------------------|
| 엔드포인트 목록 | paths 객체 |
| HTTP 메서드 | get, post, put, delete |
| 파라미터 / 요청 바디 | parameters, requestBody |
| 응답 형식 | responses, schemas |
| 그룹핑 (Auth, Posts 등) | tags |
| 설명 | summary, description |

### 3-5. 프록시가 필요한 이유

체험자 브라우저에서 직접 업로더 서버로 요청하면 **CORS 에러**가 남. 그래서 찍먹 서버가 **프록시** 역할을 해야 됨:

```
체험자 브라우저
    ↓ 요청
찍먹 서버 (프록시)
    ↓ 대신 요청 전달
업로더 서버
    ↓ 응답
찍먹 서버
    ↓ 응답 전달
체험자 브라우저
```

Spring Boot에서 프록시 구현:

```java

    @PathVariable Long demoId,
```

### 3-6. 헬스체크

서버가 살아있는지 주기적으로 확인:

```
찍먹 서버 → GET {업로더서버}/actuator/health (또는 커스텀 헬스 엔드포인트)
    ↓
200 OK → 🟢 온라인 표시
타임아웃 / 에러 → 🔴 오프라인 표시 → 리플레이 모드로 전환
```

## 4. 백엔드 리플레이 데모 (시나리오 재생)

### 4-1. 개념

무료 배포 서버는 자주 잠들거나 꺼지고, 프로젝트가 끝나면 서버를 내리는 경우가 많음. **실제로 주고받았던 요청과 응답을 녹화해서 저장해두고 재생**해주는 방식.

서버가 살아있으면 실시간 모드, 죽어있으면 자동으로 리플레이 모드로 전환됨.

### 4-2. 전체 흐름

```
"찍먹하기" 클릭
    ↓
서버 헬스체크
    ↓
  ┌─ 🟢 살아있음 → 실시간 모드 (섹션 3: 실제 API 호출)
  │
  └─ 🔴 죽어있음 → 리플레이 모드 (시나리오 JSON 재생)
                    ↓
                    Step 1: POST /api/login → 200 OK { token: "..." }
                    Step 2: GET /api/posts → 200 OK [ {...}, {...} ]
                    Step 3: POST /api/posts (토큰 없음) → 401 Unauthorized
                    ↓
                    체험자는 단계별로 요청/응답 흐름을 볼 수 있음
```

### 4-5. 시나리오 녹화 방법 (업로더용)

업로더가 시나리오 JSON을 직접 작성해도 되지만, 실제로 API를 호출하면서 **자동 녹화**하는 기능도 추후 제공 가능:

**방법 A — 직접 작성:**
위의 JSON 형식에 맞게 수동으로 작성.

**방법 B — Postman 컬렉션 변환:**
Postman에서 테스트한 컬렉션을 export → 찍먹 형식으로 변환. Postman은 요청/응답을 저장하는 기능이 있으므로 그대로 활용 가능.

**방법 C — 찍먹 내 녹화 (추후):**
실시간 모드에서 API를 호출할 때 "녹화" 버튼을 누르면 요청/응답이 자동으로 시나리오 JSON에 저장됨. 서버가 살아있을 때 녹화해두면 나중에 서버가 꺼져도 리플레이 가능.

## 5. 외부 링크 등록

zip 업로드나 API 등록 대신, **이미 배포된 URL을 등록**하는 가장 단순한 방식.

### 5-1. 동작 방식

```
업로더: "https://my-project.vercel.app" 등록
    ↓
체험자가 "찍먹하기" 클릭
    ↓
새 창에서 해당 URL로 이동 (또는 iframe 임베드)
```

### 5-2. 활용 사례

| 상황 | 예시 |
|------|------|
| 프론트 프로젝트를 Vercel에 배포해둔 경우 | `https://my-todo.vercel.app` |
| GitHub Pages로 올린 포트폴리오 | `https://kimdev.github.io/portfolio` |
| 풀스택 프로젝트를 Railway에 배포한 경우 | `https://my-chat.up.railway.app` |
| CodeSandbox에서 만든 데모 | `https://codesandbox.io/p/sandbox/...` |

### 5-3. 제한 사항

- 해당 사이트가 iframe을 허용하지 않으면 "새 창에서 실행"만 가능
- 서버가 꺼지면 체험 불가 (리플레이 시나리오를 같이 등록해두면 해결)
- 외부 URL의 콘텐츠는 찍먹이 관리할 수 없음

## 6. 업로드 시 입력 항목 정리

### 공통 항목 (모든 데모 유형)

| 항목 | 필수 | 설명 |
|------|------|------|
| 제목 | O | 데모 이름 |
| 설명 | O | 한 줄 또는 간단한 설명 |
| 태그 | O | 기술 스택 태그 (Spring, React 등) |
| 썸네일 | X | 미리보기 이미지 |
| 유형 선택 | O | 프론트 데모 / 백엔드 실시간 / 백엔드 리플레이 / 외부 링크 |

### 유형별 추가 항목

| 유형 | 추가 입력 |
|------|----------|
| 프론트 데모 | zip 파일 업로드 |
| 백엔드 실시간 | 서버 URL, OpenAPI 경로 (기본값: `/v3/api-docs`) |
| 백엔드 리플레이 | 시나리오 JSON 파일 업로드 |
| 외부 링크 | URL |

백엔드 실시간 + 리플레이를 **동시에 등록 가능** → 서버 살아있으면 실시간, 죽으면 리플레이로 자동 전환.

## 7. 보안 고려사항

| 항목 | 대응 |
|------|------|
| 프론트 데모 악성 코드 | VirusTotal API 검사 + 허용 확장자 제한 |
| 프론트 데모 XSS | 데모를 별도 도메인 (demo.dipsource.com)에서 서빙. 메인 사이트 쿠키 접근 불가 |
| 백엔드 프록시 남용 | 요청 횟수 제한 (Rate Limiting). 데모당 분당 N회 |
| 외부 링크 피싱 | URL 등록 시 스크린샷 미리보기 제공. 신고 기능 |

## 8. 구현 우선순위

| 단계 | 내용 | 난이도 |
|------|------|--------|
| **Phase 1 (MVP)** | 프론트 데모 (zip 업로드 + 정적 서빙) | 쉬움 |
| **Phase 1 (MVP)** | 외부 링크 등록 | 쉬움 |
| **Phase 2** | 백엔드 리플레이 (시나리오 JSON 재생) | 중간 |
| **Phase 2** | 백엔드 실시간 (OpenAPI 파싱 + 프록시) | 중간 |
| **Phase 3** | 시나리오 자동 녹화 | 어려움 |
| **추후** | Docker 기반 풀스택 데모 실행 | 매우 어려움 |

MVP에서는 **프론트 데모 + 외부 링크**로 시작하고, 백엔드 데모는 Phase 2에서 추가.
발표 때는 "정적 데모 → API 탐색기 → 시나리오 리플레이 → Docker 확장"이라는 로드맵을 보여주면 됨.
