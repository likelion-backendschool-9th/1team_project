# 통합 검색 Elasticsearch 도입: 구현·검증 기록

이 문서의 숫자는 모두 실제 측정값이다. 측정하지 않은 항목과 설계상 예상일 뿐인 항목은 따로 표시했다.

- 품질 재측정: `cd backend && ./gradlew searchEval` (Docker 필요, 결과는 `results/`)
- 두 결과 비교: `python3 docs/search-eval/compare.py <이전.json> <이후.json>`
- 평가 데이터: `backend/src/test/resources/search-eval/` (`corpus.json`, `queries.json`)

## 1. 구조

```text
SearchController → SearchRouter ─ 설정·장애에 따라 ─ PostgresSearchServiceImpl (기존 경로, 대체 경로)
                        │
                        └ EngineSearchService
                             ├ SearchQueryParser      전처리, 길이 검증, 해시태그 분리
                             ├ SearchPort             후보 검색 경계 (ElasticsearchSearchAdapter)
                             ├ PostgreSQL             권한·신호 확인 (findSignals)
                             ├ SearchPersonalization  숨김·차단·팔로잉·방문 기록
                             ├ SearchRanker           2차 재정렬 (순수 Java, 단위 테스트)
                             └ SearchSuggester        자판 보정 → 오타 교정 (제안만, 자동 변경 없음)

쓰기: JPA 변경 → SearchOutboxListener → search_outbox (같은 트랜잭션) → SearchOutboxWorker → Elasticsearch
```

| 항목 | 선택 | 이유 |
|---|---|---|
| 엔진 버전 | Elasticsearch 8.15.5 | Spring Boot 3.4.1이 관리하는 `elasticsearch-java` 8.15.5와 일치 (BOM에서 확인) |
| 플러그인 | nori, icu, kuromoji, smartcn | 모두 Basic 라이선스 무료. `docker/elasticsearch/Dockerfile` |
| Spring Data ES | 스타터의 클라이언트 구성·타임아웃만 사용 | dis_max·function_score·Alias 전환은 공식 Java 클라이언트로 직접 작성하는 편이 명확함 |
| 인덱스 | 대상별 4개 + 검색어 사전 1개, Alias로 읽기 | 분석·랭킹 정책이 다름. 새 버전을 채운 뒤 Alias만 옮겨 무중단 재색인 |
| 소셜 신호 | 색인하지 않고 재정렬 때 PostgreSQL 조회 | 자주 바뀌는 값의 복제·동기화 비용을 없앰 |
| 동기화 | Transactional Outbox + 폴링 | 메시지 브로커 없이 부분 실패 대응. 검색 엔진이 죽어도 변경이 유실되지 않음 |
| 자동완성 | 자모 분해 문자열에 Edge N-gram | 슾·스플 같은 조합 중 글자가 일반 접두어 검색이 됨. Completion Suggester·search_as_you_type은 자모·초성 분리가 번거로움 |

### 전환 방법

1. `SEARCH_ES_ENABLED=true`로 띄우면 색인·동기화만 켜지고 읽기는 PostgreSQL이다. 인덱스가 비어 있으면 자동으로 초기 색인한다.
2. `GET /api/v1/admin/search/status`로 문서 수를 확인한다.
3. `SEARCH_ENGINE=elasticsearch`로 읽기를 전환한다.

로컬은 `docker compose up`이면 전환까지 된 상태로 뜬다. 운영은 `docker-compose.prod.yml` 주석대로 플러그인 이미지를 레지스트리에 올리고 `COMPOSE_PROFILES=search`로 켠다.

운영 API(ADMIN 전용): `POST /api/v1/admin/search/reindex`, `/reindex/{type}/{id}`, `/reconcile`, `/outbox/retry`, `GET /status`

## 2. 평가 방법과 한계

- 고정 말뭉치: 글 약 190건(배경 글 120건 포함), 데모 10, 피드 10, 사용자 20. 요구사항의 A~F 문서를 포함한다.
- 고정 검색어 43개, 등급 0~3. 2 이상을 관련 문서로 본다. 지표는 P@10, MRR, NDCG@10, 제안어 정확도다.
- **등급은 구현자가 정한 합성 평가다.** 실제 사용자 로그가 아니므로 절대값보다 프로필 간 비교로 읽어야 한다.
- P@10은 정답 수가 10보다 적은 검색어가 많아 구조적으로 낮다.
- 측정 전 평가셋 오류 2건(문서 key 중복, 등급 누락)을 고쳤고, 그 뒤로 등급은 바꾸지 않았다.
- 재현율을 해치지 않는 동의어 결과라도 등급이 없으면 0점으로 계산된다. 예: `spring boot` 검색의 `스프링 부트 프로젝트 구조`.

## 3. 단계별 결과

각 행은 **그 단계를 구현한 시점**의 측정값이다. `results/`의 파일은 최신 코드로 다시 잰 값이라, 제안어 기능이 항상 켜진 1·2단계의 제안어 정확도가 이 표와 다르다.

| 단계 | 내용 | P@10 | MRR | NDCG@10 | 제안어 | 악화 |
|---|---|---|---|---|---|---|
| 0 | PostgreSQL LIKE | 0.1829 | 0.8150 | 0.7609 | 0.5 | - |
| 1 | BM25, 가중치 없음 | 0.2171 | 0.9553 | 0.9099 | 0 | 7건 |
| 2 | 필드 가중치, 재정렬, 스팸 감점 | 0.2220 | 0.9878 | 0.9397 | 0 | 0건 |
| 3 | 다국어, 기술 용어, 동의어, 제안어 | 0.2341 | 0.9878 | 0.9682 | 1.0 | 0건 |
| 4 | 팔로잉, 방문 기록, 숨김, 차단 | 0.2341 | 1.0000 | 0.9767 | 1.0 | 0건 |

쿼리별 비교: `stage-1-vs-0.md`, `stage-2-vs-1.md`, `stage-3-vs-2.md`, `stage-4-vs-3.md`, `final-vs-baseline.md`

### 0 → 1단계: BM25

- 개선: `#spring`·`#spring #java`가 해시태그로 동작, `C`·`java`의 단어 경계, `c#` 데모와 `react` 피드(태그 검색).
- 악화: `C#`·`C++`이 기호를 잃어 C 언어 글과 섞임. `spring` 2위가 단어 100회 반복 글. 필드 가중치가 없어 `spring jpa` 순서 역전.

### 1 → 2단계: 가중치와 재정렬

- 개선: 스팸 글이 상위권에서 사라짐, `spring boot`·`spring jpa`가 제목 일치 위주로 정렬됨. 악화 0건.
- 실험 1, 블로그 해시태그 가중치 4(요구사항 초기값) 대 1.5: NDCG 0.9416 대 0.9397로 차이가 작다. 요구사항의 정렬 순서(본문 다음 태그)에 맞춰 블로그만 1.5로 뒀다. 데모는 기술 스택이 중요해 4를 유지했다.
- 실험 2, 인기도를 끈 경우: 모든 지표가 동일했다. **이 평가셋에서는 인기도가 품질을 올렸다는 근거가 없다.** 인기도의 동작은 단위 테스트로만 검증했다.

### 2 → 3단계: 다국어와 제안어

- 첫 시도에서 `spring`이 0.93에서 0.71로 **악화**됐다. 드문 표기(`스프링`)의 IDF가 높아서 동의어 일치가 원문 일치보다 앞섰다.
- 동의어 가중치 비교: 0.6은 0.9547, 0.3은 0.9633, 0.15는 0.9634. 재현율 신호를 남기려고 0.3을 골랐다. 악화가 사라졌다.
- 버그 수정: 구문·정확 일치 가산 `should`가 `minimum_should_match` 분모에 들어가 문장 검색이 지나치게 엄격했다. 분리 후 `JWT 토큰이 만료됐을 때 처리하는 방법`의 NDCG가 0.745에서 0.947로 올랐다.
- 제안어: `sprng → spring`, `네갸ㅜㅎ → spring` 모두 정확.

### 3 → 4단계: 개인화

- `kafka`(사용자 검색)가 내 팔로잉 관계에 따라 정렬됨, 숨긴 글과 차단한 작성자의 글이 사라짐.
- `p_visited`는 개인화 전에도 2위라 **평가셋으로는 방문 가산의 효과를 측정할 수 없었다.** 효과는 동작 테스트로 검증했다(3회 방문 시 순위 상승, 2회는 그대로, 다른 검색어·오래된 방문은 미적용, 관련도가 크게 낮은 글은 못 올라옴).

### 기존 대비 유일한 악화

`스프링`(NDCG 1.0 → 0.997). 정답 문서가 모두 상위에 있고 순서만 조금 바뀌었다.

## 5. 성능 (실측)

환경: 로컬 Mac, 단일 노드 ES(힙 1GB), PostgreSQL 16, 글 10만·피드 10만·데모 1만·사용자 1천. 기존 k6 도구(`backend/scripts/search-check`)를 재사용했다. ES 값은 **재정렬 캐시를 끈 상태**다.

| 요청 | PostgreSQL p50 / p95 (ms) | Elasticsearch p50 / p95 (ms) |
|---|---|---|
| 결과 많음 `spring` | 1,206 / 2,927 | 70 / 92 |
| 여러 단어 `spring jpa` | 2,007 / 2,111 | 70 / 112 |
| 0건·오타 `sprnig` | 2,187 / 2,346 | 34 / 46 |
| 1~4건 `sprng` | 2,237 / 2,358 | 36 / 49 |
| 자동완성 `spr` | 193 / 210 | 4 / 6 |
| 자동완성 한글 `스플` | 218 / 231 | 6 / 8 |

- 동시 사용자 부하(S3, 최대 50명, ES 경로): p50 57ms, p95 144ms, p99 241ms, 오류 0%, 커넥션 풀 대기 0. **PostgreSQL 경로의 S3는 이번에 다시 재지 않았다.**
- 구간별 평균: Elasticsearch 검색 10.4ms, 재정렬 0.41ms, PostgreSQL 신호 조회 0.5~1.3ms. 전체 검색 한 번에 PostgreSQL 쿼리는 대상 수에 비례하고 후보 수와 무관하다(N+1 없음).
- 초기 색인: 약 20.9만 문서 35초. 인덱스 크기 글 57MB, 피드 16MB, 데모 2.6MB, 사용자 0.3MB.
- 색인 반영 지연: 피드 생성 후 검색까지 1.16초(폴링 간격 2초에 좌우). 삭제는 PostgreSQL 확인으로 0.03초 뒤 결과에서 사라짐.
- ES 정지 시: 검색 200 응답(약 1초, PostgreSQL 속도), 서버 health는 UP 유지.

측정하지 않은 항목: 다중 노드, 운영 환경 메모리 사용량, 실제 검색어 분포에서의 품질.

## 6. 구현 범위

### 부분 구현 또는 미구현

| 항목 | 상태와 이유 |
|---|---|
| 블로그·데모 쓰기 경로의 동기화 | 글 CRUD가 아직 스텁이라 실제 경로로 검증하지 못함. JPA 리스너는 준비됐고 피드·회원으로 검증함 |
| 링크 미리보기 텍스트 색인 | DB에 해당 데이터가 없음 |
| 피드 조회수 신호 | `feeds`에 조회수 컬럼이 없어 0으로 처리 |
| 조회수 갱신 | 글·데모의 `view_count`·`play_count`를 올리는 코드가 아직 없어 신호가 0일 수 있음 |
| 차단 API | `blocks` 테이블만 있고 API가 없음. 검색 반영은 DB 데이터로 검증함 |
| "의미 있는 방문" | 검색 결과 클릭 + 30분 재방문 제외로 정의. 체류 시간은 측정하지 않음 |
| 벌크 쿼리로 바꾼 상태 | JPA 이벤트로 잡히지 않음. 매일 도는 정합성 점검이 복구 |
| search_after·PIT | 쓰지 않음. 페이지 번호 API를 유지하기 위해 상위 200건 재정렬 + 60초 캐시로 일관성을 맞춤. 캐시 만료 뒤 깊은 페이지는 순서가 달라질 수 있고, 10,000건 이후는 빈 결과 |
| 재색인 동시 실행 방지 | 서버 프로세스 안에서만 막음. 다중 인스턴스에서는 별도 잠금이 필요함 |
| 전체 탭 통합 순위 | 요구대로 대상별 묶음. RRF는 구현하지 않음 |

### 달라진 동작

| 변경 | 이유 |
|---|---|
| 0건일 때 자동 교정(`correctedQuery`)을 ES 경로에서 하지 않음 | 요구사항의 "자동 변경 금지". 대신 `suggestedQuery`로 제안. PostgreSQL 경로는 그대로 |
| 일반 검색 최소 2글자 (ES 경로) | 요구사항. `C`, `R` 등 사전 용어는 예외 |
| 본문 부분 문자열 검색 없음 (`ecur` → `Security`) | 형태소·단어 단위 검색으로 전환. 닉네임은 N-gram으로 부분 일치 유지 |
| `op` 생략 시 auto | 기본은 and와 같고 긴 문장만 75% 일치. 명시적 and/or는 그대로 |
| 응답 필드 추가 | `suggestionType`, `relaxedMatch`. 기존 필드는 유지 |
| 프론트 검색 페이지 | 기존 코드가 백엔드 응답 형태와 맞지 않아(`posts.content`) 함께 수정 |

### DB·인덱스 변경

테이블 추가 3개: `search_outbox`, `search_hidden_results`, `search_visits` (`docs/테이블정의서.md` 12장). 기존 테이블 변경 없음. 인덱스: `dipsource_post|demo|feed|user|suggest` Alias.

## 7. 설계 질문에 대한 답

1. **왜 Elasticsearch인가**: LIKE는 형태소·단어 경계·문서 빈도를 다룰 수 없다. 같은 평가셋에서 NDCG 0.761 → 0.977, 10만 건 p95 2.9초 → 92ms로 측정됐다.
2. **관련도 기준**: BM25 + 필드 가중치(`SearchProperties`), 단어별 dis_max로 필드를 넘나드는 and 검색.
3. **제목·본문·태그 구분**: 대상별 가중치. 숫자 부스트로 보장되지 않는 정확 일치는 재정렬에서 별도 등급으로 처리.
4. **검색어 반복 방지**: BM25 빈도 포화 + 색인 시 품질 계수. 반복 신호가 두 개 이상일 때만 감점해서 정상 문서를 보호.
5. **다국어와 자판 오입력**: 언어별 서브필드를 모두 색인하고 검색어 문자에 맞는 필드만 조회. 자판 변환은 사전에 있는 후보만 제안하고 검색어를 바꾸지 않음.
6. **인기도·개인화**: 1위 대비 상대 관련도에 상한 있는 가산을 곱한다. 차이가 상한(인기도 15%, 방문 10%, 팔로잉 25%)보다 크면 뒤집히지 않는다.
7. **정합성**: Outbox로 유실 방지, 처리 시 원본 재조회로 멱등, 외부 버전으로 순서 보장, 결과 반환 직전 PostgreSQL 재확인, 매일 정합성 점검.
8. **품질 검증**: 고정 평가셋으로 단계별 수치 비교. 합성 평가의 한계는 2장에 적었다.
9. **AI 검색 확장**: 후보 검색은 `SearchPort` 구현을 추가해 붙이고, `SearchRanker`와 응답 형식은 유지한다. 하이브리드는 `SearchPort` 구현 안에서 결과를 합친다.

## 8. 남은 과제

- 실제 검색 로그로 평가셋을 보강(현재는 합성)
- 표현이 다른 문장 검색은 키워드로 한계가 있어 의미 검색 후보
- 사전 관리 화면(현재는 `tech-terms.json` 수정 후 배포)
- 일본어·중국어는 기본 동작만 검증
- 검색어 사전은 10분 주기로 전체 재구축(규모가 커지면 증분 필요)
