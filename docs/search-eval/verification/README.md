# 통합 검색 추가 검증 보고서

10단계 구현(커밋 `7b858ef`) 이후 진행한 추가 검증 기록이다. 기존 결과는 [../README.md](../README.md)에 그대로 두었고, 이 문서의 수치는 모두 이번에 새로 측정한 값이다.

**판정 기준**

| 표시 | 의미 |
|---|---|
| 통과 | 실제로 실행했고 예상과 일치 |
| 실패 | 실제로 실행했고 예상과 다름. 코드는 고치지 않고 `[한계]` 테스트로 현재 동작을 고정 |
| 부분 | 일부 경로만 검증 |
| 미검증 | 실행하지 못함. 성공으로 간주하지 않음 |

1~9장은 `35c02bd` 시점의 **수정 전 기록**이다. 이후 검색 관련 문제를 고친 결과는 [10장](#10-문제-수정-결과-7d6ee68)에 따로 적었다.

## 1. 신규 평가셋

| 항목 | 내용 |
|---|---|
| 목적 | 기존 43개 검색어로 튜닝한 결과가 처음 보는 검색어에서도 유지되는지 확인 |
| 환경 | Testcontainers PostgreSQL 16, Elasticsearch 8.15.5(플러그인 이미지), 기본 설정 |
| 입력 | `holdout-queries.json` 50개, `holdout-corpus.json` 문서 82건 + 배경 글 120건 |
| 실행 | `cd backend && ./gradlew searchEval -PevalLabel=es-first --tests '*HoldoutEsEval' --tests '*PostgresBaselineEvalTest*'` |
| 동결 | 결과를 보기 전에 커밋 `a565894`로 고정. 이후 정답·설정을 바꾸지 않음 |
| 예상 | 기존 평가셋(NDCG 0.977) 근처이거나 튜닝 효과만큼 하락 |

**실제 결과**

| 범주 | 검색어 수 | ES MRR | ES NDCG@10 | PostgreSQL MRR | PostgreSQL NDCG@10 |
|---|---|---|---|---|---|
| 문장형 | 11 | 1.000 | 0.970 | 0.091 | 0.091 |
| 띄어쓰기 | 8 | 1.000 | 1.000 | 0.625 | 0.519 |
| 한영혼용 | 6 | 1.000 | 0.986 | 1.000 | 0.986 |
| 특수문자 | 9 | 1.000 | 1.000 | 1.000 | 0.984 |
| 대상별 | 5 | 1.000 | 1.000 | 0.800 | 0.800 |
| **전체(순위 평가 39개)** | 39 | **1.000** | **0.989** | **0.641** | **0.614** |

| 제안어 범주 | 검색어 수 | ES 정확도 | PostgreSQL 정확도 |
|---|---|---|---|
| 오타 | 8 | 0.875 | 1.000 |
| 자판 오입력 | 3 | 0.667 | 0.000 |
| **전체** | 11 | **0.818** | **0.727** |

**틀린 사례 (수정하지 않음)**

| 검색어 | 기대 | 실제 | 원인 |
|---|---|---|---|
| `reactt` | react 제안 | 제안 없음 | 입력이 후보를 포함하면 어형 변화로 보는 규칙(`token`/`tokens`용)이 `reactt`/`react`도 막음 |
| `flsnrtm` | 리눅스 제안 | 제안 없음 | 변환은 맞음. 말뭉치에 리눅스 글이 없어 "결과가 있을 때만 제안" 규칙에 걸림. 평가셋 구성 문제에 가까움 |

**판정과 한계**

- 수치는 측정했지만 **이 값이 실제 품질을 보장하지는 않는다.** 문서와 정답을 구현자가 작성해서 검색어와 어휘가 많이 겹친다. 실제 사용자 표현에서는 더 낮을 수 있다.
- 오타 교정 정확도는 PostgreSQL이 더 높다(1.000 대 0.875). 다만 PostgreSQL은 결과가 없으면 검색어를 자동으로 바꾼다.
- 정답이 쉬운 검색어가 많아 NDCG 차이를 세밀하게 구분하지 못한다. 실제 검색 로그 기반 평가가 필요하다.

## 2. PostgreSQL·Elasticsearch 동일 조건 비교

| 항목 | 내용 |
|---|---|
| 목적 | 같은 환경·데이터·캐시 조건에서 동시 사용자별 성능과 자원 사용량 비교 |
| 환경 | 8장의 머신, 같은 jar(`35c02bd`), JVM 힙 1GB, 두 컨테이너 모두 실행, 색인 구성요소 양쪽 모두 활성 |
| 입력 | 글 100,035건, 피드 100,012건, 데모 10,008건, 사용자 1,008명. 검색어 8개 혼합, 전체 탭 첫 페이지 |
| 캐시 조건 | 측정 전 같은 검색어 3회 데우기. 재정렬 캐시는 첫 페이지에 쓰이지 않으므로 애플리케이션 결과 캐시는 양쪽 다 없음. PostgreSQL 버퍼 캐시와 ES 내부 캐시는 각자 기본값 |
| 부하 | 사용자별 검색 후 1초 대기, 단계당 60초, 요청 타임아웃 30초, PostgreSQL·ES 순서를 바꿔 2회 |
| 실행 | `cd backend/scripts/search-check && ./compare-engines.sh setup && ./compare-engines.sh run && ./compare-engines.sh report` |
| 예상 | ES가 빠르고, 동시 사용자가 늘수록 차이가 커짐 |

**실제 결과 (2회 평균)**

| 사용자 | 엔진 | p50 | p95 | p99 | RPS | 오류율 |
|---|---|---|---|---|---|---|
| 1 | PostgreSQL | 1,276ms | 2,266ms | 2,289ms | 0.4 | 0% |
| 1 | Elasticsearch | 86ms | 113ms | 128ms | 0.9 | 0% |
| 10 | PostgreSQL | 2,499ms | 3,407ms | 3,788ms | 2.9 | 0% |
| 10 | Elasticsearch | 80ms | 136ms | 196ms | 9.2 | 0% |
| 50 | PostgreSQL | 10,105ms | 23,502ms | 28,744ms | 3.5 | 0.64% |
| 50 | Elasticsearch | 61ms | 215ms | 481ms | 45.8 | 0% |
| 100 | PostgreSQL | 22,902ms | 30,001ms | 30,001ms | 3.6 | 23.25% |
| 100 | Elasticsearch | 303ms | 481ms | 782ms | 78.9 | 0% |

RPS는 사용자별 1초 대기를 포함한 값이다. 자원 사용량(회차별, CPU는 평균, 메모리는 최대)은 [engine-comparison.md](engine-comparison.md)에 있다.

| 100명 기준 (1회차) | PostgreSQL 경로 | Elasticsearch 경로 |
|---|---|---|
| PostgreSQL CPU | 1,038% | 47% |
| Elasticsearch CPU | 1% | 366% |
| 백엔드 JVM CPU | 5% | 89% |
| 커넥션 풀 대기 최대 | 118 | 0 |
| 메모리 | PostgreSQL 520MB | Elasticsearch 1,851MB |

**판정과 한계**

- 통과. PostgreSQL 경로는 50명에서 이미 CPU를 모두 써서 포화된다.
- k6, 앱, DB, ES를 **한 대의 노트북에서 함께** 돌렸다. 값은 비교용이고 운영 성능이 아니다.
- ES는 메모리를 약 1.8GB 더 쓴다. 운영 서버 메모리 예산을 먼저 확인해야 한다.
- 2회 반복이라 분산을 통계적으로 판단하기엔 부족하다.
- 측정 중 다른 프로세스(`dipsource-db-local`, Next.js 개발 서버)가 유휴 상태로 있었다.
- 측정하지 않음: 다중 노드, 2페이지 이후 부하, 색인 쓰기와 검색을 동시에 건 혼합 부하.

응답 시간이 전 구간에서 늘었고 특히 50명 구간의 꼬리 지연이 커졌다. 응답 직전에 상위 200건 전체를 PostgreSQL로 재확인하는 비용이 원인으로 추정되지만, 구간별로 분리해 측정하지는 않았고 노트북 측정이라 변동도 포함돼 있다. PostgreSQL 경로와의 차이는 그대로 크다(100명 p95 약 30초).

**남은 한계**

- `searchId`는 10분 유휴 후 만료되고, 만료되거나 보내지 않으면 순서가 바뀔 수 있다.
- 탐색 중 앞 페이지의 글이 삭제·숨김되면 뒤 페이지가 한 칸 당겨져 글 하나를 건너뛸 수 있다.
- 문서 자체가 거절된 실패는 재시도 한도가 그대로 있다. 분류 로직은 단위 테스트만 했다.
- 유료 글의 색인 대기가 처리되지 못하면 그동안 그 글은 검색에서 빠진다.
- 대체 경로에서 `C` 같은 허용된 한 글자 검색은 빈 결과다.
- 자동완성 확인은 앞쪽 후보 16개만 대상으로 하고, 글 색인 반영(수 초) 뒤에 효과가 난다.
- 재시도 한도를 넘는 약 32분 이상의 실제 정지는 수행하지 않았고 실패를 반복 실행해 재현했다.
- 기존 인덱스에 `content_hash`를 추가하는 시작 시 매핑 갱신은 오류 로그 없음만 확인했고, 값이 빈 문서가 점검으로 채워지는 경로는 별도로 시험하지 않았다.
- 프론트의 `searchId` 전달은 타입 검사와 린트까지 했고 브라우저에서 확인하지 않았다.
- 미검증 유지: 글 수정·삭제 API의 다른 경로, 데모 쓰기, 회원 탈퇴·정지, 차단 API, 다중 서버.
