# 피드 추천 알고리즘 설계

> 찍먹 피드의 추천 시스템 구조와 구현 방향을 정리한 문서
>
> **기준:** PostgreSQL 16, Spring Boot 3.4.1, ERD_v2
>
> **최종 수정:** 2026-11-03

---

## 1. 전체 구조 — 3단계 진화

서비스 성장 단계에 따라 추천 방식이 점진적으로 확장되는 구조.
데이터가 없는 초기부터 유저가 수천 명 이상 쌓이는 시점까지 끊김 없이 동작.

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│   Phase 1. 지식기반 추천                                      │
│   (가입 직후, 데이터 없음)                                     │
│                                                              │
│           ↓ 유저 활동 쌓이기 시작                              │
│                                                              │
│   Phase 2. 점수기반 추천 + 콘텐츠 기반 필터링 + 트렌딩          │
│   (유저 수백 명, 좋아요/댓글 데이터 축적)                       │
│                                                              │
│           ↓ 유저 수천 명 이상, 행동 데이터 충분                  │
│                                                              │
│   Phase 3. 데이터 기반 추천 (협업 필터링 등)                    │
│   (확장 영역 — 현재 프로젝트 범위 외)                           │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**현재 프로젝트 목표: Phase 1 + Phase 2 구현 (완료)**

### Phase 전환 로직

`user_tag_profile` 테이블에 해당 사용자의 데이터가 있으면 Phase 2, 없으면 Phase 1.

```java
boolean hasActivity = userTagProfileRepository.existsByIdUserId(userId);
if (hasActivity) → 점수 기반 (Phase 2)
else → 지식 기반 (Phase 1)
```

## 2. Phase 1 — 지식기반 추천

### 개념

유저의 행동 데이터가 없을 때, 유저가 **직접 입력한 정보**를 기반으로 추천하는 방식.
콜드 스타트(데이터 없음) 문제를 해결하는 역할.

### 적용 시점

- 서비스 초기 (전체 데이터가 부족할 때)
- 신규 가입자 (개인 활동 이력이 없을 때)

### 구현 방식

#### 2-1. 회원가입 시 관심 태그 선택

```
"관심 있는 기술을 선택하세요 (3~5개)"

[ #Spring ]  [ #React ]   [ #Python ]  [ #Unity ]
[ #DevOps ]  [ #AI ]      [ #Flutter ] [ #Node ]
[ #Java ]    [ #TypeScript ] [ #Docker ] [ #Kotlin ]
```

유저가 선택한 태그를 `user_interest_tags` 테이블에 저장.

#### 2-2. 태그 기반 피드 조회

선택한 관심 태그가 달린 피드를 우선 노출하고, 트렌딩 피드와 반반 섞어서 보여줌.

```sql
-- 관심 태그가 달린 피드 조회
SELECT f.*
FROM feeds f
JOIN feed_tags ft ON f.id = ft.feed_id
WHERE f.status = 'ACTIVE'
  AND ft.tag_id = ANY(:interestTagIds)
  AND f.user_id != :userId
  AND (:cursorId IS NULL OR f.id < :cursorId)
GROUP BY f.id
ORDER BY f.id DESC
LIMIT :size
```

#### 2-3. 관심 태그도 없는 경우

관심 태그를 아예 선택하지 않은 사용자는 최신 피드로 대체.

#### 2-4. 피드 구성 비율 (Phase 1)

| 구성 | 비율 | 소스 |
|------|------|------|
| 관심 태그 피드 | 50% | 관심 태그가 달린 피드 최신순 |
| 트렌딩 | 50% | 인기 급상승 피드 |

## 3. Phase 2 — 점수기반 추천

### 개념

유저의 실제 활동 데이터(좋아요, 댓글, 팔로우 등)를 기반으로 점수를 계산하고, 점수가 높은 순서로 피드를 정렬하는 방식. 세 가지 요소를 조합.

```
피드 점수 = ① 기본 점수 정렬 + ② 콘텐츠 기반 필터링 + ③ 인기도 기반 트렌딩
```

---

### 3-1. 기본 점수 정렬

모든 피드 글에 점수를 매겨서 정렬.

#### 점수 공식

```
score = 10                        -- 기본 점수 (모든 글 동일)
      + follow_bonus              -- 팔로우한 사람이면 +50
      + like_count                -- 좋아요 수
      + comment_count * 2         -- 댓글 수 (가중치 2)
      + repost_count * 3          -- 리포스트 수 (가중치 3)
      - hours_elapsed             -- 경과 시간 (오래될수록 감점)
      + tag_match_score           -- 태그 매칭 점수 (콘텐츠 기반)
```

#### 각 항목 설명

| 항목 | 값 | 이유 |
|------|-----|------|
| 기본 점수 | +10 | 신규 유저 글도 최소 10점에서 시작. 노출 기회 보장 |
| follow_bonus | +50 | 팔로우한 사람의 글을 우선 노출 |
| like_count | +1 per | 좋아요는 가장 기본적인 반응 지표 |
| comment_count | +2 per | 댓글은 좋아요보다 참여도가 높은 행동 |
| repost_count | +3 per | 리포스트는 가장 높은 가중치 |
| hours_elapsed | -1 per hour | 시간이 지나면 자연스럽게 하락 |
| tag_match_score | +5 per tag (max 20) | 콘텐츠 기반 필터링 점수 |

#### SQL 구현

```sql
SELECT f.*,
    (10
     + CASE WHEN f.user_id = ANY(:followingIds) THEN 50 ELSE 0 END
     + f.like_count
     + f.comment_count * 2
     + f.repost_count * 3
     - EXTRACT(EPOCH FROM (NOW() - f.created_at)) / 3600
     + COALESCE(tm.tag_match_score, 0)
    ) AS score
FROM feeds f
LEFT JOIN (
    SELECT ft.feed_id,
           LEAST(SUM(tp.weight) * 5, 20) AS tag_match_score
    FROM feed_tags ft
    JOIN user_tag_profile tp
         ON ft.tag_id = tp.tag_id AND tp.user_id = :userId
    GROUP BY ft.feed_id
) tm ON f.id = tm.feed_id
WHERE f.status = 'ACTIVE'
  AND f.created_at > NOW() - INTERVAL '7 days'
  AND f.user_id != :userId
  AND f.user_id NOT IN (
      SELECT blocked_id FROM blocks WHERE blocker_id = :userId
  )
  AND (:cursorId IS NULL OR f.id < :cursorId)
ORDER BY score DESC, f.id DESC
LIMIT :size
```

### 3-2. 콘텐츠 기반 필터링 (Content-Based Filtering)

#### 개념

유저가 좋아요/댓글/북마크한 글들의 태그를 분석해서 "이 사람이 뭘 좋아하는지" 파악하고, 비슷한 태그의 새 글을 우선 노출하는 방식.

#### 동작 원리

**1단계 — 유저 태그 프로필 생성**

유저의 활동 이력에서 태그를 집계.

```
유저 A의 최근 활동:
  좋아요 → "JWT 인증 구현기"         태그: #Spring, #Security
  좋아요 → "JPA N+1 해결법"          태그: #Spring, #JPA
  북마크 → "Spring Batch 입문"       태그: #Spring, #Batch
  댓글   → "React 상태관리 비교"     태그: #React, #Frontend

→ 유저 A의 태그 프로필:
   #Spring: 4회 (가중치 4)
   #Security: 1회
   #JPA: 1회
   #Batch: 1회
   #React: 1회
   #Frontend: 1회
```

**2단계 — 새 글과 유사도 계산**

```
새 글: "Spring Security OAuth2 적용기"  태그: #Spring, #Security, #OAuth

유저 A 프로필과 비교:
  #Spring   → 가중치 4 → 매칭
  #Security → 가중치 1 → 매칭
  #OAuth    → 가중치 0 → 미매칭

tag_match_score = min((4 + 1) * 5, 20) = 20점 (상한)
```

**3단계 — 피드 점수에 합산**

`tag_match_score`가 기본 점수 정렬에 반영됨.

#### 태그 프로필 업데이트 시점

| 이벤트 | 태그 가중치 변화 |
|--------|----------------|
| 좋아요 | 해당 글 태그 +1 |
| 댓글 작성 | 해당 글 태그 +1 |
| 북마크 | 해당 글 태그 +1 |
| 좋아요 취소 | 해당 글 태그 -1 |

구현: `TagWeightService.increaseWeight(user, feedId, 1)` 호출

#### 한계와 보완

| 한계 | 보완 방법 |
|------|-----------|
| 콜드 스타트 (활동 없음) | Phase 1 지식기반으로 대체 |
| 필터 버블 (비슷한 것만 보임) | 트렌딩 50% 혼합으로 새로운 글 노출 |

### 3-3. 인기도 기반 추천 — 트렌딩 (Trending)

#### 개념

단순히 좋아요가 많은 글이 아니라, **최근 짧은 시간 안에 반응이 빠르게 몰리는 글**을 찾아서 노출하는 방식.

#### 왜 단순 좋아요 순이 안 되는가

```
글 A: 3개월 동안 좋아요 200개  → 오래된 인기글
글 B: 2시간 만에 좋아요 30개   → 지금 뜨는 글

단순 좋아요순이면 A가 항상 위. 하지만 지금 뜨는 건 B.
```

#### 시간 가중치 방식 (Time Decay)

최근 반응일수록 높은 가치를 부여.

```
trending_score = 최근 1시간 반응 수 * 10
               + 최근 6시간 반응 수 * 3
               + 최근 24시간 반응 수 * 1
```

#### SQL 구현

```sql
SELECT f.*,
    (
        (SELECT COUNT(*) FROM feed_likes fl
         WHERE fl.feed_id = f.id
         AND fl.created_at > NOW() - INTERVAL '1 hour') * 10
      + (SELECT COUNT(*) FROM feed_likes fl
         WHERE fl.feed_id = f.id
         AND fl.created_at > NOW() - INTERVAL '6 hours') * 3
      + (SELECT COUNT(*) FROM feed_likes fl
         WHERE fl.feed_id = f.id
         AND fl.created_at > NOW() - INTERVAL '24 hours') * 1
    ) AS trending_score
FROM feeds f
WHERE f.status = 'ACTIVE'
  AND f.created_at > NOW() - INTERVAL '7 days'
  AND (:cursorId IS NULL OR f.id < :cursorId)
ORDER BY trending_score DESC, f.id DESC
LIMIT :size
```

## 4. 팔로잉 피드 (`?type=following`)

내가 팔로잉한 사람들의 글만 최신순으로 보여줌. 점수 계산 없음.

```sql
SELECT f.*
FROM feeds f
WHERE f.status = 'ACTIVE'
  AND f.user_id = ANY(:followingIds)
  AND (:cursorId IS NULL OR f.id < :cursorId)
ORDER BY f.id DESC
LIMIT :size
```

## 5. 비로그인 사용자

로그인하지 않은 방문자는 개인화 불가. 대신:

| 구성 | 비율 | 소스 |
|------|------|------|
| 트렌딩 | 50% | 인기도 기반 (트렌딩 점수) |
| 최신 | 50% | 최근 글 시간순 |

- 차단/본인 글 필터링 없음
- `status = 'ACTIVE'` 필터만 적용

## 6. 필터링 — 제외 조건

모든 피드 쿼리에 공통으로 적용하는 WHERE 조건

| 조건 | SQL | 설명 |
|------|-----|------|
| 삭제/블라인드 제외 | `f.status = 'ACTIVE'` | |
| 차단 유저 제외 | `f.user_id NOT IN (SELECT blocked_id FROM blocks ...)` | |
| 본인 글 제외 | `f.user_id != :userId` | 추천 피드에서만 |
| 7일 이내만 | `f.created_at > NOW() - INTERVAL '7 days'` | |
| 커서 페이지네이션 | `(:cursorId IS NULL OR f.id < :cursorId)` | |

## 7. 커서 기반 페이지네이션

프론트엔드가 무한 스크롤을 사용하므로 offset 방식 대신 커서(keyset) 방식을 사용.

### offset vs cursor

```
offset 방식: 페이지가 깊어질수록 느려짐
  SELECT ... OFFSET 10000 → DB가 10000행을 읽고 버림

cursor 방식: 항상 일정한 속도
  SELECT ... WHERE f.id < :cursorId LIMIT 20
```

### API 응답 형태

```json
{
  "content": [ ... ],
  "nextCursor": "1042",
  "hasNext": true,
  "size": 20
}
```

- `nextCursor`: 마지막 피드의 ID
- `hasNext`: 다음 페이지 존재 여부
- 프론트에서 `nextCursor` 값을 다음 요청의 `cursor` 파라미터로 넘기면 이어서 조회

## 11. 점수 가중치 튜닝 가이드

점수 공식의 가중치는 서비스 운영하면서 조정이 필요함.

### 초기 권장값

```
기본 점수:       10
팔로우 보너스:    50
좋아요 가중치:    1
댓글 가중치:      2
리포스트 가중치:   3
시간 감점:       -1 per hour
태그 매칭:       +5 per tag (max 20)
```

### 조정이 필요한 신호

| 현상 | 원인 추정 | 조정 방향 |
|------|-----------|-----------|
| 팔로우한 사람 글만 보임 | follow_bonus가 너무 높음 | 50 → 30으로 낮추기 |
| 오래된 글이 계속 상단 | hours_elapsed 감점이 약함 | -1 → -2로 강화 |
| 신규 글이 너무 안 보임 | 기본 점수가 낮음 | 10 → 20으로 올리기 |
| 트렌딩이 너무 자주 바뀜 | 1시간 가중치가 너무 높음 | 10 → 5로 낮추기 |
| 비슷한 글만 추천됨 | 태그 매칭 점수가 높음 | max 20 → max 10 |

-- 피드 조회 성능
CREATE INDEX idx_feeds_status_created ON feeds(status, created_at DESC);

## 13. Phase 3 — 확장 방향 (참고용)

현재 프로젝트 범위에는 포함되지 않지만, 데이터가 충분히 쌓인 이후 확장 가능한 방향.

### 협업 필터링 (Collaborative Filtering)

"나랑 비슷한 유저가 좋아한 글"을 추천하는 방식.

```
유저 A: 글 1, 3, 5에 좋아요
유저 B: 글 1, 3, 7에 좋아요
→ A와 B는 취향 유사 → A에게 글 7 추천
```

- 필요 조건: 유저 수천 명 이상, 좋아요 데이터 수만 건 이상

### 소셜 그래프 기반

팔로우 관계를 활용한 2촌 추천.

```
내가 A를 팔로우 → A가 B의 글에 좋아요 → 내 피드에 B의 글 노출
```
